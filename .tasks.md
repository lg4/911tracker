## OPEN
- **T12 — data validation (provenance + durability):** two halves. (a) Provenance: guarantee
  scraped data == what was live at fetch time — capture source checksum + fetched-at timestamp per
  row at ingest; store per-tick provenance (source URL, count, hash) in a meta table so a presented
  feature traces back to a verified tick; detect drift between table state and a fresh fetch before
  serving; flag rows whose status changed after storage (statusHistory exists for this).
  (b) Durability/consistency across copies: tables are LRS today with no replication story — the
  cheap hobby-scale answer is a near-zero-cost backup lane, e.g. timer-triggered function copying
  the table into a second table or blob-container archive (same infra, no new service), plus a
  documented restore path in docs/runbook.md. Prefer 0/serverless options over any added tier.

- **T19 — quick-window date drift (UTC vs local):** `daysAgo(n)` builds dates from
  `Date.now() - n*24h` then truncates via `toISOString().slice(0,10)`, i.e. a UTC-midnight anchor,
  while `/api/incidents` parses `?since&until` as `${date}T00:00:00Z` / `T23:59:59Z`. For US
  Eastern users, local late evening (e.g. 7pm EDT = midnight UTC) makes "Today" resolve to
  *tomorrow's* calendar day — the window shifts by up to a full day. Fix: compute the local
  calendar date (not UTC) for the button defaults and document that the API treats them as UTC
  midnights; or push tz-aware bounds down into the function.
